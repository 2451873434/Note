# qspi控制器驱动注册失败——错误码(-2)

## 问题现象

​	使用`6.6`版本内核在`D3000M`上进行`qspi`测试时，`qspi`控制器驱动注册失败，报错如下：

```shell
[	43.961965] OF: /soc/qspi@18006000: could not get #clock-cells for /soc/i2c@28009000
[	43.962890] phytium-qspi: probe of 18006000.qspi failed with error -2
```

## 问题原因

​	这里很容易将第一行的报错误认为是警告，从而将其忽略。实际上，本例中设备树的`qspi`控制器描述中的`clock = <0x11>`，而设备树中的时钟描述没有`phandle = <0x11>`的时钟描述。这就会导致`qspi`控制器驱动获取设备描述的时钟时出错，错误码为`-2`，也就和第二行的报错相对应。

> ​	笔者第一次遇到该问题时，想当然的认为设备树描述中的`clock = <0x11>`肯定能够找到对应的时钟描述，所以是从第二行的报错信息入手。这导致多走了些弯路，但是最后分析出的问题原因是一样的。下面介绍通过第二行报错信息查找问题原因。
>
> ​	首先可以看出`qspi`控制器驱动注册失败并且错误码为`-2`，分析`qspi`控制器驱动注册函数，发现能够直观看出来的返回的错误码一般为`-ENOMEM(-12)`和`-EINVAL(-22)`。那可以推测错误码`-2`是由驱动注册函数中调用的函数的返回值。~~那我们就需要找到驱动注册函数中所有可能出错导致`return ret`的地方，并且分析所有给`ret`赋值的函数~~。显然，按删除线的方法去分析的话太过复杂，难以实现。我们可以通过加打印的方式定位出报错的位置为`qspi->clk = devm_clk_get(dev, NULL)`。这时笔者就怀疑是设备树的`qspi`描述中的`clock = <0x11>`有问题。

## 解决方法

​	设置设备树的`qspi`控制器描述的`clock`属性为正常的时钟值。

```shell
clocks {
	clk600mhz {
		compatible = "fixed-clock";
		#clock-cells = <0x0>;
		clock-frequency = <0x23c34600>;
		phandle = <0x10;>
	};
};
soc {
	qspi@18006000 {
		/* ...... */
		clocks = <0x10>;
		/* ...... */
	};
};
```
