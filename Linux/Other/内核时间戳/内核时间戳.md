# 内核时间戳

> 以下内容来自`Deepseek`

### 1. `CNTVCT_EL0` 的复位行为

根据ARM架构参考手册，`CNTVCT_EL0`（虚拟计数寄存器）在发生**热复位（Warm reset）**时，其值会复位成一个架构上不可预知（UNKNOWN）的值。

*   **这意味着**：如果S3休眠唤醒过程被芯片或系统视为一次热复位，那么该寄存器的硬件值会丢失并变成一个随机数。
*   **并非所有休眠都复位**：需要强调的是，并非所有硬件平台在S3休眠时都会复位该计数器。有些平台的系统计数器在低功耗状态下可能继续运行，有些则可能停止。因此，`CNTVCT_EL0` 在唤醒后是否复位，完全取决于具体硬件的设计。

> 飞腾的D2000和D3000的设计会在低功耗时对`CNTVCT_EL0`进行复位操作，其值会变成0。

### 2. 时间戳跳变？

如果 `CNTVCT_EL0` 的值在唤醒后变成了一个不可预知的新值，那么任何未经修正就直接读取该寄存器来获取时间的代码，都会得到错误的时间戳，从而产生跳变。

一个典型的例子是虚拟机（VM）场景。当QEMU暂停（stop）一个ARM虚拟机后再恢复（cont）时，如果 `CNTVCT_EL0` 没有随之停止，就会导致客户机（Guest OS）在恢复后读取到错误的时间，进而触发“软锁定（soft lockup）”等时间相关的内核错误。

### 3. 操作系统的补偿机制

然而，在实际的Linux等操作系统中，**这种跳变通常不会直接导致系统时间错误**，因为内核有专门的机制来处理这种情况。

*   **时间补偿**：Linux内核的计时子系统（Timekeeping）会识别出像ARM通用定时器这类在休眠时可能停止或不连续的时钟源。
*   **持久时钟（Persistent Clock）**：为了在休眠期间维持准确的时间，内核会使用一个在休眠时仍能运行的“持久时钟”（Persistent Clock）或依赖实时时钟（RTC）来记录休眠的时长。
*   **唤醒后的校正**：系统唤醒后，时间维护核心（timekeeping core）会读取持久时钟或RTC，计算出系统休眠了多长时间，然后用这个时长来校正系统时间。这样一来，即使 `CNTVCT_EL0` 的值发生了跳变，系统时间也会被修正到正确值。

### 总结

| 场景              | `CNTVCT_EL0` 行为 | 对时间戳的影响             |
| :---------------- | :---------------- | :------------------------- |
| **硬件复位**      | 复位成UNKNOWN值   | **直接读取会产生跳变**     |
| **硬件保持/停止** | 值保持不变或停止  | 无跳变，或通过补偿修正     |
| **有OS补偿**      | 即使复位          | **系统时间被校正，无跳变** |

总而言之，**硬件上**，寄存器复位必然导致其读数跳变；但**软件上**，现代操作系统（如Linux）具备完善的休眠唤醒时间补偿机制，能够有效消除这种硬件跳变对系统时间的影响。



## 补充1

**Persistent Clock（持久时钟）和RTC（实时时钟）在Linux内核中是两个功能相似但定位、精度和访问方式都不同的概念。**

简单来说，Persistent Clock是内核为精确测量休眠时间而设计的**纯内部接口**，而RTC则是用于维护“墙上时间”的**通用硬件设备**。

它们的主要区别如下：

| 特性         | **Persistent Clock (持久时钟)**                              | **RTC (实时时钟)**                                           |
| :----------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **核心定位** | 内核内部的时间测量接口                                       | 一个通用的硬件时钟设备，提供人可读的日期时间                 |
| **主要用途** | 精确测量系统在休眠（Suspend）期间的持续时间，用于唤醒后校正系统时间 | 在系统断电时保持时间不丢失，用于在启动时初始化系统时间（`HCTOSYS`） |
| **精度**     | **高**，可以提供纳秒（nsec）级精度                           | **低**，通常只提供秒级精度                                   |
| **访问时机** | 可在**中断关闭**的极早期或极晚期调用                         | 访问可能依赖中断，不适合在时间核心的临界区使用               |
| **实现方式** | 可能是一个在休眠时继续计数的**自由运行计数器**（如ARM的32kHz计数器） | 通常是一个独立的、带电池的硬件芯片，通过I2C/SPI等总线连接    |
| **使用者**   | **内核时间维护核心（Timekeeping core）** 专用                | 内核其他部分及**用户空间**均可通过`/dev/rtc`等接口访问       |

### 为什么需要这两个概念？

这主要是由**历史原因**和**技术限制**造成的。

1.  **历史的演进**：早期时间管理是架构相关的。后来Linux创建了通用的`persistent_clock()`接口来统一访问CMOS等时钟。与此同时，又发展出了独立的、更通用的RTC驱动框架。这导致了两套功能重叠但又各有侧重的体系并存。

2.  **核心的技术矛盾**：内核时间维护核心需要在**中断关闭**的极端情况下（如刚刚唤醒时）读取时间以计算休眠时长。而很多RTC设备依赖I2C/SPI等总线，这些总线的访问需要中断，因此不适合在此时使用。`Persistent Clock`接口正是为了解决这个矛盾而生，它只要求底层硬件能在中断关闭时被访问。

### 实际应用中的关系

在实际的ARM等系统中，`Persistent Clock`常常由一颗在休眠时依然能工作的**32kHz计数器**来实现。它的值从零开始，用于精确测量休眠时长。

*   **测量休眠**：系统休眠前读取Persistent Clock的值，唤醒后再次读取，两者的差值就是精确的休眠时长。
*   **恢复时间**：内核用这个精确的时长来补偿系统时间。如果Persistent Clock不可用，内核才会退而求其次，使用精度较差、误差较大的RTC方案。
*   **同步RTC**：当系统通过NTP同步到精确时间后，内核会通过`update_persistent_clock()`接口将正确的时间写回RTC，确保断电后时间不丢失。

### 总结

可以把它们的区别理解为：

*   **RTC**是一个**通用的硬件设备**，负责在断电时保存“**现在几点了**”这个信息，精度为秒级。
*   **Persistent Clock**则是一个**内核专用的软件抽象接口**，负责在系统休眠时精确记录“**睡了多久**”，精度可达纳秒级，以满足内核在高精度时间校正上的需求。

两者相互配合，共同确保系统时间在休眠前后既准确又连续。



## 补充2

除了Persistent Clock和RTC，Linux内核确实还有第三种，也是**最理想**的休眠时间补偿方式：**Nonstop Clocksource（不间断时钟源）**。

### 什么是Nonstop Clocksource？

Nonstop Clocksource是一种在系统进入S3休眠等低功耗状态时，**依然能够持续运行并计数**的硬件时钟源。

一个典型的例子是现代x86处理器上的**TSC (Time Stamp Counter)**。在较新的CPU上，TSC在休眠期间也不会停止。

### 内核如何使用它？

Linux内核通过一个专门的标志 `CLOCK_SOURCE_SUSPEND_NONSTOP` 来识别这种时钟源。

在系统唤醒时，时间维护核心（Timekeeping core）会按照一个**优先级顺序**来尝试补偿休眠时间：

1.  **首先**，检查当前的clocksource是否具有 `CLOCK_SOURCE_SUSPEND_NONSTOP` 标志。
2.  **如果是**，就直接读取该时钟在休眠期间累积的计数值（`cycle_delta`），并将其转换为纳秒，然后注入到系统时间中。**这种方式完全不需要依赖任何外部设备**。
3.  **如果不是**，才会退而使用Persistent Clock或RTC。

### 三种方式的对比

为了更清晰地理解，这里将三种方式做个对比：

| 特性         | **Nonstop Clocksource (不间断时钟源)**     | **Persistent Clock (持久时钟)**        | **RTC (实时时钟)**                     |
| :----------- | :----------------------------------------- | :------------------------------------- | :------------------------------------- |
| **核心原理** | 硬件时钟**自身在休眠时不停**               | 内核在休眠前后读取一个**不停**的计数器 | 读取一个带电池、**独立运行**的时钟芯片 |
| **数据来源** | 当前系统使用的主时钟源（如TSC）            | 一个专用的、可在中断关闭时访问的计数器 | 一个独立的硬件芯片（如CMOS）           |
| **优先级**   | **最高**（最优先选择）                     | 次选                                   | 最低（最后的选择）                     |
| **精度**     | **极高**，与系统主时钟源精度一致           | 较高                                   | 较低（通常为秒级）                     |
| **主要优点** | **最精确**，无额外硬件依赖，无累积误差     | 精度较高，可在中断关闭时访问           | 通用性强，几乎所有平台都有             |
| **主要风险** | 休眠时间过长可能导致计数器**回绕（wrap）** | 需要平台提供特殊硬件支持               | 精度低，电池可能失效，存在时间漂移     |

### Nonstop Clocksource的潜在风险与应对

虽然Nonstop Clocksource很理想，但它也有一个需要关注的风险：**计数器回绕（Wrap）**。

如果系统休眠的时间太长，以至于时钟源的计数器计数超过了它的最大值，就会发生回绕，从零重新开始。这会导致内核计算出的休眠时间远小于实际值。

内核开发者也意识到了这个问题。可能的应对策略包括：

*   **硬件设计**：确保时钟源的计数器宽度足够大（如64位），使得回绕周期远大于任何可能的休眠时间（例如，TSC的回绕周期可能长达数百年）。
*   **软件预警**：内核可以设定一个定时器（alarm），在计数器即将回绕前唤醒系统，进行一次“心跳”更新，防止回绕。



**Nonstop Clocksource（不间断时钟源）和 Persistent Clock（持久时钟）在Linux内核中确实都用于解决休眠期间的时间补偿问题，但它们的本质、角色和优先级截然不同。**

简单来说，**Nonstop Clocksource是“硬件自带”的属性，而Persistent Clock是“软件抽象”的接口**。前者是内核优先使用的理想方案，后者是兼容老旧或受限硬件的备选方案。

以下是它们的核心区别：

### 1. 本质不同：属性 vs 接口
- **Nonstop Clocksource（属性）**：这是**当前系统主时钟源**（如x86的TSC、ARM的Generic Timer）自带的一个**硬件特性标志**（`CLOCK_SOURCE_SUSPEND_NONSTOP`）。它表明这个主时钟在休眠时依然在跑，不是一个独立的硬件设备。
- **Persistent Clock（接口）**：这是内核中定义的一组**回调函数**（`struct persistent_clock_ops`）。它是一个软件层面的抽象层，用于对接各种底层硬件（可能是SoC内置的32kHz计数器，也可能是外部RTC），其目的就是专门供时间核心在休眠前后调用。

### 2. 工作机理不同：直接算 vs 间接读
- **Nonstop Clocksource**：唤醒后，内核**直接**读取该时钟当前的周期计数值（cycles），与休眠前保存的计数值做减法，得到精确的周期差（`cycle_delta`）。内核直接将其换算成纳秒加到系统时间上。**整个过程不需要调用任何外部接口。**
- **Persistent Clock**：唤醒后，内核**必须**调用其抽象接口（如 `read_persistent_clock64()`），让底层驱动去读取特定硬件的值，然后将这个值返回给内核。内核拿到的通常是封装好的“秒/纳秒”绝对值。

### 3. 精度与数据格式不同
- **Nonstop Clocksource**：数据格式是**原始周期计数**，它拥有与主时钟源同等的高精度（通常是纳秒级），且分辨率极高。
- **Persistent Clock**：数据格式通常是经过换算的**绝对时间（秒/纳秒）**。受限于底层硬件（如常见的32kHz晶振），其精度往往较低，通常只能达到毫秒甚至秒级。

### 4. 优先级与内核逻辑（最关键区别）
在Linux内核的时间维护核心（Timekeeping）中，它们的优先级是硬编码的：

1. **第一选择**：内核首先检查当前使用的clocksource是否带有 `CLOCK_SOURCE_SUSPEND_NONSTOP` 标志。**如果有，内核会完全跳过Persistent Clock的读取**，根本不调用它。
2. **备选方案**：只有当主时钟源**不具备**Nonstop属性时，内核才会退而求其次，去调用 `read_persistent_clock()` 接口来获取休眠时间。

### 5. 对硬件的要求不同
- **Nonstop Clocksource**：要求**主时钟源**（即平时跑系统时用的那个高频时钟）在休眠时不能断电。这通常依赖SoC内部复杂的电源管理设计，且要保证休眠时间足够长而不发生计数器回绕（Wrap）。
- **Persistent Clock**：只需平台上**额外存在一个**能记录时间的硬件即可。它可以是SoC内部超低功耗的Always-On计数器，也可以是独立的外部RTC芯片。它对主时钟是否停止完全不关心。

---

### 形象类比

把系统主时钟比作汽车的**主里程表**（精度极高，记录行驶里程），把Persistent Clock比作司机手里的**秒表**。

- **Nonstop Clocksource** = 车子熄火时，**主里程表依然在转动**记录时间。重新点火后，只需看里程表走了多少公里，就知道停了多久，**极其精确且即时**。
- **Persistent Clock** = 车子熄火后**主里程表停了**。但司机在熄火时按下了秒表开始计时，重新点火时再看秒表走了多久。如果司机忘了按秒表（硬件不支持），或者秒表精度不高，补偿就会不准。**内核只在主里程表停转（非Nonstop）时，才会去读这个秒表。**

### 总结
- **Nonstop Clocksource** 是**硬件能力**的体现，代表“主时钟自己就不停”，是最高效、最精确的方案。
- **Persistent Clock** 是**软件兼容层**，代表“主时钟虽停，但我有别的辅助工具记录时间”，是内核为了兼容各种硬件而设计的兜底机制。

**一句话核心结论**：只要内核发现有Nonstop Clocksource，Persistent Clock就会被彻底“无视”；只有当硬件无法提供不间断主时钟时，Persistent Clock才作为“救火队员”登场。
